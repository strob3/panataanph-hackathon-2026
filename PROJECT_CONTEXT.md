# PanataanPH

## Project Overview

PanataanPH is a verified directory of Philippine relief drives and fundraisers. It aims to help donors evaluate fundraising campaigns by presenting organizer-provided information, supporting documents, evidence completeness, and review status in one place.

The project addresses the difficulty of distinguishing well-documented relief campaigns from campaigns with incomplete or questionable information, especially during disasters such as typhoons and floods.

## Core Features

- **Public Campaign Directory:** Browse, search, and filter relief campaigns by location, cause, urgency, and verification status.
- **Campaign Submission:** Allow organizers to submit campaign details and upload supporting documents.
- **Organizer Accounts:** Login is required for submissions and private campaign/fund-report management. Admins/LGU reviewers verify organizer identity before publication.
- **Donation Methods:** Publish organizer-supplied donation QR images and payment instructions only after campaign approval; supporting evidence remains private.
- **Funds Transparency:** Publish dated received/spent reports after admin review, with target progress and recorded totals. These are organizer reports, not automatic payment reconciliation.
- **Local AI Document Extraction:** Extract text from uploaded PDFs and images, then use a locally running LLM to structure relevant information.
- **Evidence Completeness Score:** Calculate a transparent score based on submitted evidence and predefined rules.
- **Admin Review Dashboard:** Let admins inspect original documents, review extracted information, investigate discrepancies, and make final decisions.
- **Campaign Reporting:** Allow users to report concerns for administrative review.

## Local AI Implementation

The Local AI feature assists admins by reducing the time required to read documents and manually transcribe relevant information. It does not independently verify document authenticity, determine whether an organization is legitimate, or classify campaigns as fraudulent.

### Processing Workflow

1. An organizer uploads a supporting document.
2. The FastAPI backend receives the file.
3. A PDF text parser extracts selectable text from text-based PDFs. PaddleOCR extracts text from scanned documents and images.
4. FastAPI sends the extracted text and extraction instructions to Ollama's local API.
5. Ollama runs Qwen3 4B to identify relevant fields and return structured JSON.
6. FastAPI validates the response using a defined schema and stores the results.
7. The frontend displays the extracted fields alongside the original document.
8. An admin reviews the information and decides whether to approve the campaign, reject it, or request additional information.

### Example Extracted Fields

- Document type
- Permit number
- Issuing authority
- Organization name
- Purpose of solicitation
- Issue date
- Expiration date
- Beneficiaries, when explicitly stated

The model must return null for missing information rather than inventing values. Extracted information is subject to OCR errors and model mistakes, so admins must be able to inspect the original document.

## Verification Score

The Verification Score ranges from 0 to 100 and is calculated by deterministic application logic, not generated by the LLM.

The score represents the completeness and consistency of submitted evidence. It is not a guarantee of authenticity, legitimacy, or proper use of donations.

The minimum score for ordinary approval eligibility is 80/100. Scores never publish campaigns automatically. Human approval, a verified organizer account, and explicit review and resolution of warnings and major inconsistencies are required. Admins can request additional private evidence or approve below the threshold with an explicit exception and recorded reason. Public details identify such exceptions. Requested evidence returns the campaign to `under_review` and clears its previous score. Missing the threshold does not label the campaign fraudulent. Revoking account verification removes its campaigns from public endpoints.

Potential criteria include:

- Applicable permits or authorizations
- Organizer identity and registration information
- Consistency between organizer and payment details
- Campaign information completeness
- History of previously reviewed campaigns

Legal requirements and the applicability of specific permits must be reviewed separately. Missing or inconsistent information should trigger further review rather than an automatic fraud accusation.

## Technology Stack

- **Frontend:** React/Vite, TypeScript, Tailwind CSS (integrated responsive frontend)
- **Backend:** Python, FastAPI
- **OCR:** PaddleOCR
- **Local LLM runtime:** Ollama
- **LLM:** Qwen3 4B
- **Database:** SQLite for the hackathon MVP
- **Document processing:** PDF text extraction plus OCR for scanned documents
- **Storage:** Private local filesystem for uploaded documents

## Architecture

React/Vite communicates with FastAPI through a same-origin API proxy. SQLite stores accounts, revocable sessions, campaign ownership, private document metadata, donation QR metadata, fund reports, findings, and review history. Manual admin/LGU verification is implemented. Document parsing, OCR, and Ollama inference remain planned phases; they must stay local when implemented.

For the hackathon demonstration, the frontend, backend, model runtime, database, and document processing run on the same host machine. After the model and dependencies have been downloaded, the core document-analysis workflow must be demonstrated without an internet connection.

## Security and Privacy

- Keep uploaded identity documents and permits private by default.
- Restrict access to administrative functions and private files.
- Validate uploaded file types and sizes.
- Treat document contents as untrusted input.
- Do not send uploaded documents to external AI APIs.
- Do not expose sensitive document contents on public campaign pages.
- Record administrative decisions and reasons for review.
- Use fictional campaigns and documents in demonstrations.

## Hackathon Scope

The goal is to deliver a working end-to-end MVP within 24 hours.

### Required
- Campaign directory and detail pages
- Campaign submission and document uploads
- Local OCR and LLM extraction
- Structured output validation
- Evidence completeness scoring
- Admin review and status management
- Offline demonstration

### Optional
- Campaign reporting
- Advanced filters
- Detailed review history
- Additional UI polish

### Out of Scope
- AI-based fraud prediction
- Automatic claims of document authenticity
- Automatic approval or rejection by the LLM
- Automatic verification against external government databases
- Donor accounts, notifications, and production-scale deployment unless time permits

## Definition of Done

The MVP is ready when a fictional campaign can be submitted with a supporting document, processed locally through OCR and the LLM, displayed with structured extracted fields, evaluated by the rules-based score, and reviewed by an admin. The workflow must remain functional offline after initial setup and model download.
